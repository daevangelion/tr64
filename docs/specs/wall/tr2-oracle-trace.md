# Tomb Raider II: retail PC behaviour trace

Game: Tomb Raider II, Steam appid 225300. Executable: Windows PC `Tomb2.exe`, 912896 bytes, SHA-256 `fd9c91d14d54540b3e00c9bedafeef9e4ddb1e9542adc9f29170c7f19b1a657b`.
Reader: WallRE2. Date: 2026-11-21. Evidence: observations under Wine 11.22 on <remote-host>, compared with authored level data and pinned retail rules. Scope: The Great Wall and Venice from a fresh PC campaign, not PlayStation or saved starts. The first schema-22 trace verifies Venice's native opening with no input; driving and other routes have separate scopes.

## Headless start and sampling

**Established.** The licensed Steam executable runs under Wine 11.22 with a private WoW64 prefix and a private copy of the game. An Xvfb screen at 1024×768 with depth 24 hosts the game's own full-screen Software 256 Colour Renderer at 1024×768. Its Disable FMV option skips the films. The title ring starts on Lara's Home; select Passport, open it, then confirm New Game. The first playable level is The Great Wall, not the training courtyard. No physical disc or Steam client was needed with this installed game copy. A positive control for the level is Lara at (62976, 1536, 23040), room 35, 1000 HP and 1800 air before the first update, followed by actual movement under gravity in that room.

**Established — time and presentation.** A logic tick represents 1/30 second of normal-speed gameplay, not 1/30 second of host elapsed time. These fixtures use one logic tick per subsequent draw and the fixture seed 3547461959 for both random streams at tick 0. Those are capture conditions, not promises about ordinary retail startup or drawing; the game can ordinarily batch gameplay updates and start with different seeds. Under the fixture conditions it still draws, runs its sound updates and advances both random streams normally after tick 0. Tick 0, with input zero, is the initial playable state before the first logic update. Tick 1 and later are sampled once after each logic tick, after items, Lara, camera and the level clock, before the next draw. A single record does not imply that all the objects in it moved in the same order as Lara.

## Wire conventions and input

**Established — serialization.** The schemas use ASCII JSON Lines, no optional spaces, one LF after each record. There are N+1 records for an N-mask script. Objects have the fixed field order shown below; all numeric values are decimal integers, including booleans 0 or 1. Schema 22 uses JSON `null` only where specified for removed hulls. Only the final `hash` is a string, eight lowercase hex digits: FNV-1a-32 (offset 2166136261, multiplier 16777619, modulo 2³²) over the entire record with the `hash` property removed, including the final closing brace but not the LF. Vectors are X/Y/Z in game units, Y increasing downward. Rotation arrays are pitch, yaw and roll, signed 16-bit turns (65536 per revolution). The table lists signed fields unless marked unsigned. World position and split floor differences use signed 32-bit integers; ordinary animation, room, item, timer, speed, angle and health quantities are signed 16-bit. Unused references are −1; no process address is a reference.

**Established — input.** A nonempty script contains one or more unsigned decimal integers, separated by ASCII space, tab, line feed or carriage return, with those separators also allowed at either end. Signs, nondecimal characters, unlisted bits and integers outside 0–123902 are rejected. Leading zeros are allowed. Combine ordinary controls by bitwise OR; 123902 combines all ordinary bits. There is no separate grammar limit on the number of masks; capture time limits still apply. The first mask applies to tick 1. Each describes controls held for one gameplay tick, not an event timestamp. The recorded `input` preserves the original mask, including cancelled pairs. These are fixture masks, not retail input numbers. Title and passport navigation are outside the sampled script. Inventory bit 2048 is only admitted as a standalone press matched by a main-ring selection in the manifest.

**Established — native key-ring confirmation.** `rusty-key` uses the same mask grammar. Its `keyConfirmation` manifest entry describes one Action that opens the native key ring during the named gameplay update. Confirm the sole carried key by its public ring type. Do not insert it into the ring at placement and do not advance Lara, the items or the camera while the menu is open. There is no separate mask or record for the paused selection. Once the menu closes, complete that same gameplay update. The saved campaign time includes the menu interval, which is separate from the number of input masks; menu draws can also advance the presentation stream. In this fixture, 50 menu ticks on update 610 make `save.time` jump from 609 to 660 and cause 50 extra presentation advances in addition to the ordinary advance, with no gameplay RNG advance. The duration is a fixture condition, not a rule that every key prompt in retail takes 50 ticks.

**Established — native main-ring shotgun selection.** In `shotgun-tiger`, mask 2048 appears alone on tick 2. The native main ring opens before the next gameplay update, without advancing Lara, the items or the camera in the menu. Select the carried ring type 158 at zero-based position 2, using two Left selections and then Action. There is no native stock grant and no mask or sample for the intervening menu. The manifest's `shotgunSelection` describes the first gameplay update after confirmation: tick 3, when the saved clock jumps from 2 to 90 (87 additional ticks), main selection changes from 0 to 2, and Lara begins drawing the already carried gun. The presentation random state advances 91 times between these samples; the count is measured, not an equivalence between menu clock ticks and random draws. The duration is specific to this menu fixture.

**Established — native main-ring medipack selection.** In `medipacks`, the two standalone Inventory presses at ticks 168 and 190 each open the native main ring before the next gameplay update. In each opening select Right once from position 0, then complete the Action confirmation; the small is last among six entries and the large last among the five that remain. No intermediate menu input or update appears in the logic script or trace. The medipacks already belong to Lara as starting stock. Between samples 168 and 169 the saved clock goes from 168 to 256 and presentation advances 88 times; between 190 and 191 it goes from 277 to 359 and presentation advances 82 times. No gameplay draw occurs in either of these whole intervals. The saved clock includes the sum of the additional pauses from their respective `tick` values onward. See [the medicine rules](tr2-triggers-and-interaction.md#medipacks-from-the-main-ring-q-cartui-01).

## Placed starts before tick 1

**Established — fixture input, not a retail start option.** An input may start at its first byte with the line `place X Y Z yaw room`. The word `place` is lowercase and each of the five decimal arguments is separated from its predecessor by one or more ASCII spaces or tabs. No leading whitespace before `place`, plus signs, or extra arguments. A minus sign is allowed; leading zeros are allowed. The coordinates must fit signed 32-bit world units, yaw must fit −32768…32767, and the room must be a valid ordinal in the pinned level. The line can end with spaces or tabs, then LF or CRLF. Its bytes after `p`, including LF, cannot exceed 127. After this line follow the ordinary mask bytes; at least one mask is still required and the first one still applies to tick 1.

**Established — what changes.** Start the actual level and complete the ordinary [fresh campaign setup, including the initial camera view](tr2-lara-start.md#camera-seed-placement-and-the-opening-view). Seed both fixture random streams as usual. Before sampling tick 0, move only Lara: use the supplied three position coordinates and yaw, with zero pitch and roll. Keep her fresh dry Stand with current and desired state 2, clip 11 at frame 185 here, no queued state, zero horizontal and vertical speeds, no gravity, and dry water state. In particular, the initial travel angle is zero regardless of the body yaw. Do not round or snap the supplied position. Keep the rest of the fresh Lara state, including her pre-check water distance of 100, health, air, free hands, and holstered pistols.

**Established — membership and floor seed.** The placement supplies live membership, not a request to find another room from her position. It must name a dry room with X/Z inside that room's sector grid and a stored floor click other than −127. If membership changes, remove Lara from the old room's item order without disturbing the other items, and insert her before the destination room's current first item. If it does not change, keep the order. Store the destination sector's signed live floor byte times 256; the sample uses that sector directly, without room links, sloping height or shaped objects. This is the ordinary dry start's coarse floor convention, now applied at the selected position. The first actual tick can resolve another room or floor.

**Established — what stays fresh.** Leave the camera exactly as it is at the authored fresh-start sample, even if it is in a different room from placed Lara; do not seed it again or move its target with her. There is no extra camera update or room query at placement. The first gameplay tick applies the normal item, movement, floor and camera rules from that state. Placement does not activate items, evaluate triggers, change the inventory or statistics, alter world geometry, advance either random stream, or add a gameplay tick. Placement metadata belongs in the manifest, not in the record.

**Established — positive control.** `place 62976 1536 23040 0 35` followed by the same 300 masks as `stand` produced a trace byte-identical to all 301 published `stand` records. This tests placement at the authored spawn, including the opening view and the subsequent fall and slide, not only equality of one initial pose.

**Established — cutting existing history.** At `travel` tick 32 Lara is (62976, 3063, 23540), 500 units along +Z from her original X/Z, with yaw 0 and room 35. Placing her there and using exactly the masks from `travel` 33–319 preserves that position and yaw at the comparison point, but starts in Stand 11/185 with horizontal speed zero instead of slide 70/1143 at speed 50. The stored floor is initially 2304 rather than 3063, and `waterDistance` is 100 rather than 32512. The first real tick reacquires that fixed eye and takes the local slope reaction; the target and later camera motion still differ. Only the sector digest differs among world digests at the cut and its first tick; all world digests agree from the second tick onward. Gameplay RNG stays at the fixture seed in both continuations, but the presentation history restarts. The departure and automatic gaze both begin at placed tick 176 (208 in the aligned comparison), four ticks later than `travel` 204. ## Record fields

Schemas 20 and 21 top-level order: `schema`, `tick`, `level`, `lara`, `camera`, `active`, `save`, `inventory`, `world`, `rng`, `hash`. `tick` is the nonnegative ordinal. `level` is the campaign number: 1 for the published 20 and 21 fixtures, 2 for the Venice dialect below. `active` contains the level item slots in their live update order at the sampling point, not sorted by object or by distance. It does not duplicate Lara. It may contain spawned items that have entered the same update set; transient visual/audio effects with separate lifetimes are not entries. It also does not mean a list of everything drawn or every sleeping placement.

Schema 20 is not schema 4 with a new number. In particular its arm records, inventory entries and selections, level statistics and world digests have their own layouts and meanings. Use the definitions below even where names are shared. In particular, `world[3]` is the digest of room partner numbers defined here.

| Item field, in order | Meaning |
|---|---|
| `index`, `type` | Item slot 0–255; public object type 0–264 in authored PC data. |
| `pos`, `rot`, `room` | World origin, signed rotation, and live room membership (a room ordinal 0–254). Membership is not a promise the origin is inside the authored bounds of that room. |
| `anim`, `frame` | Level animation index and authored frame number. Frame is not relative to the current clip's start. |
| `state`, `goal`, `next` | Current, desired, and queued animation state numbers; a zero queued state means no additional request. |
| `flags`, `health` | Unsigned 16-bit item flags, including five trigger mask bits (9–13), once bit 8, and reverse bit 14. `health` is the signed current item health, including sentinel values for some retired or non-targetable items. |
| `hSpeed`, `vSpeed`, `timer` | Signed horizontal and downward movement speeds per tick; item countdown with −1 used for expiry where applicable. The stored speed is not necessarily that tick's net displacement after collision. |
| `roomFloor`, `hitMask`, `visibleMask` | Stored signed world floor height (−32512 can mean no usable floor); unsigned 32-bit touch and visible mesh masks. |
| `status`, `gravity`, `wasHit`, `collidable` | Activity status: 0 inactive, 1 active, 2 deactivated, 3 invisible; whether gravity, recent hit and body collision flags are set, each 0/1. Active update order is still taken from `active`, not inferred from the status alone. |

### Creature extension in schema 21

**Established — extension only.** Schema 21 keeps the input grammar, sample point, field order and hash rule of schema 20. An `active` entry for a creature occupying one of the five navigation slots appends `ai` after `collidable`. Otherwise it omits `ai`; no null placeholder is added. This never changes the Lara record. Active-list presence alone does not ensure a brain: a newly awakened or evicted creature can be in the list without one. Removing every `ai`, setting `schema` to 20 and recomputing each `hash` gives the exact schema-20 projection.

| `ai` fields, in order | Established meaning |
|---|---|
| `slot`, `enemy`, `mood` | Navigation slot 0–4, followed by the tracked item's slot (−1 when none) and mood: 0 bored, 1 attacking, 2 escaping, 3 stalking. `enemy` is the current choice, not the fallback Lara position a creature can use when it has no enemy. |
| `jointYaw`, `maxTurn`, `flags` | `jointYaw` is an array of two signed 16-bit angles, −32768…32767, in authored use order. The tiger uses the first for head yaw. `maxTurn` is a nonnegative signed 16-bit angle, 0…32767, retained for the next ordinary turn, not the amount it turned on this tick. `flags` is unsigned 16-bit species state, 0…65535; for the tiger it is the strike latch (0 allows damage, 1 already hit). |
| `box`, `targetBox`, `requiredBox`, `nextBox` | Stored current box, installed search destination, requested destination, and the link from the stored current box toward the destination. Each is a signed 16-bit reference: −1 for none, otherwise an ordinal from 0 through the level's box count minus one (1077 in The Great Wall, 624 in Venice). A link can belong to an older search. The stored `box` need not contain the body's rendered origin. |
| `headBox`, `tailBox`, `search`, `boxSearch` | Stored first and last queued box, with the same box reference domain. `headBox = −1` is empty; `tailBox` can still name the last removed box until the search next checks for work. Do not normalize the stale tail: `spider-bite` slot 10 at 194 has head −1 and tail 714. `search` and `boxSearch` are unsigned 16-bit words, 0…65535: current search generation and generation of the stored current box. `boxSearch` high bit (32768) marks a blocked route; other bits give the generation. If there is no current box, `nextBox` is −1 and `boxSearch` is 0. |
| `step`, `drop`, `fly`, `blockMask`, `zoneCount` | Signed 16-bit movement limits: `step` 0…32767 (maximum rise), `drop` −32768…0 (negative maximum drop), `fly` 0…32767 (vertical flight speed; zero for ground navigation). `blockMask` is an unsigned 16-bit mask, 0…65535, of forbidden box overlap flags. `zoneCount` is a nonnegative signed 16-bit count, at most the level's box count (1078 in The Great Wall, 625 in Venice). |
| `destination`, `waypoint` | Each is a three-element array of signed 32-bit world coordinates `[X,Y,Z]`, with each component in −2147483648…2147483647. They give the requested destination and most recently resolved steering point. If `targetBox` is −1, both vectors are `[0,0,0]`: the creature has no initialized route points to record. A death clip can retain the last points of a live route. These are sampled choices, not a claim that a stationary creature turned toward them. |

### Venice extension in schema 22

**Contract — extension and validation.** Schema 22 has the schema-21 fields, in their original order, with `boats`, `race`, `mines`, then `effectsUsed`, immediately after `rng` and before `hash`. Use the same sample point, mask grammar, placement grammar, ordered `active` list, and all four world hash byte streams. This dialect uses `level` 2 and the Venice level manifest below. Room ordinals and room/world hashes refer to the selected level, not The Great Wall's 84 rooms. Venice has 155 room ordinals and 625 box ordinals. Do not change the earlier schemas, fixtures, or their projections. To compare only common fields of a Venice sample, remove `boats`, `race`, `mines` and `effectsUsed`, set `schema` to 21, and recompute the line hash without changing `level`; the result is a common-field projection, not a schema-21 Great Wall fixture.

**Contract — placed hulls.** `boats` always has two entries, sorted by original placement slot: 26, then 91. These are the authored type-14 hulls, not gondolas. Each entry has `index`, `present`, `item`, `hull`, in that order. `index` is the permanent level slot. `present` is 1 while the hull remains in the level, including an unused, stationary or dormant hull; it becomes 0 on destruction and removal. A removed entry keeps its `index` with `present` 0 and has `item` and `hull` both `null`. For `present` 1, `item` is the complete common item record (from `index` through `collidable`, without `ai`) and its `index` equals the outer index. A hull on `active` must be present and has the same common fields in both places. A stationary hull is not marked active merely because it is sampled. Read Lara's `vehicle` slot independently; do not infer or clear it from a hull's presence or proximity.

| `hull` field, in order | Meaning |
|---|---|
| `turn` | Signed 32-bit steering angle per tick, retained for the next hull stride. |
| `bowVSpeed` | Two signed 32-bit suspension descent speeds in units per tick, lateral −300 then +300 at the two points 750 toward the bow. The centre descent remains `item.vSpeed`. |
| `bank` | Signed 16-bit steering contribution to hull roll, in turn units. This is the stored bank (six times the steering turn used for the movement), not six times the newly sampled `turn` after the driver's controls. The bank is already included in `item.rot[2]`. |
| `terrainYaw` | Signed 16-bit terrain correction retained for the next yaw step, separate from `turn` and the hull's stored yaw. |
| `supportY` | Signed 32-bit centre **suspension** target. It is water height minus 5 when there is water, otherwise the sampled floor without subtracting 5. If neither is usable, retain the numeric no-height value −32512. The boat's ordinary `item.roomFloor` instead stores the sampled floor minus 5 (−32517 when that floor is missing). See [the distinct bow and stern samples](tr2-venice-objects.md#hull-motion-collision-and-departure). |

**Established statically — initial hulls and exclusions.** Each hull's authored origin and room establish its initial placement. The six scalar hull quantities in the five keys above start at zero; the first active update gives `supportY` its physical value. An additional stored value, filtered motor pitch, also starts at zero but only affects the motor's sound. It does not affect movement, collision, triggers or wake allocation and is omitted. The hull and clock placements corroborate the slot identities; neither this initialization nor the contract asserts playback parity yet.

**Contract — race actuators.** `race` has `timer`, `latch`, `active`, `leaves`, in that order. The first three fields come from authored clock slot 76, type 216. `leaves` is an array in slot order 73 (type 110), then 74 (type 111), each with `index`, `timer`, `latch`, `active` in that order. Sample all three placed items even when dormant. `timer` is the stored signed 16-bit count in ticks (zero untimed, positive for time remaining, −1 on ordinary expiry). `latch` is the five activation bits as a number 0–31 (item flag bits 9–13, with bit 9 becoming value 1); full mask is 31. `active` is 0/1 according to whether that item is in the current active list, not inferred from its timer or mask. A threshold can write a leaf's timer without giving it a full latch or waking it. For active items these samples agree with the common record. Do not infer any actuator's timer from another or from `save.time`. See [the authored race](tr2-venice-objects.md#lock-and-the-clock-tower-race).

**Contract — mine chain.** `mines` has `chain`, then `items`. `chain` is the stored 0/1 chain-in-progress flag for the level. `items` always lists the six authored type-222 placements in ascending slot order 106 through 111, each with `index`, `spent`, `active`, in that order. `spent` is the placed item's spent flag (0/1, item flag bit 8), not an inference from mesh, proximity or a missing active entry. `active` is 0/1 membership in the current active list, independent of `spent`. This preserves spent or dormant state outside `active`. The [mine rule](tr2-venice-objects.md#glass-gondolas-and-aquatic-mines) establishes the first explosion separately from the gameplay draws for later mines.

**Contract — effect count.** `effectsUsed` is one integer from 0 through 100: count all occupied shared room-effect slots at the same post-update sample as the other fields, regardless of visibility or room. It includes surviving wakes, explosions, splashes, blood, fragments and any effects made later in the same tick by Lara. It is neither the number of allocations during the tick nor a substitute for the capacity rule. Matching it checks total occupancy under contention; the count alone does not identify individual effects or prove their allocation order.

**Established statically — wake and shared effect occupancy.** Wake uses the same [100 room-effect slots](tr2-great-wall-creatures.md#small-and-giant-spiders) as blood and other effects. An active hull attempts three sprites, in lateral order −300, 0, +300, if its final Y equals the raw water-height sample minus 5 and its **post-collision, post-control speed** is nonzero. Use the signed speed after any correction, throttle, steering nudge or empty-hull coasting for eligibility, the descent test and sprite speed. Do not use the earlier speed that moved the hull. One presentation draw is made for the group even if no slot is free. At each successful allocation with signed hull speed below 64, take one more presentation draw (0–32767). Subtract 64 from the absolute speed, multiply by that draw, and divide by 32768 rounding down for the initial descent. At signed speeds 64 or more descent starts at zero without that extra draw. Failure consumes no per-sprite draw and does not replace another effect. Every allocated sprite starts with 20 effect ticks remaining and signed movement speed one quarter of the final hull speed rounded down. Its first effect update runs on the creation tick because boats update before the effects.

**Established statically — wake retirement.** On each effect update decrease the remaining count. At zero, or if entry descent is positive, retire before moving; otherwise do the horizontal wake step. If descent is nonzero, move Y by the old descent and then add 6. A descent that reaches exactly zero thereafter stays zero: it waits for the timer instead of entering positive descent. A positive result retires on the next update. There is no separate room-distance or visibility test for retirement and no draw in the update. These rules account for wake occupancy; other effects can contend for the same slots and contribute to `effectsUsed`. Wake never occupies a level-item slot or imparts damage, force or triggers.

**Contract — fresh Venice entry.** Run the licensed game into Venice by the already measured [native `level-finish` transition](tr2-great-wall-level.md#exit-cut-and-venice-carry): replay the exact finish input before the Venice capture, use Action on cut control poll 3 and Confirm on statistics control poll 3. No Great Wall gameplay, movie or menu record precedes Venice tick 0 in this file. The carried loadout is pistols, shotgun with 12 pellet units, one unlit spare flare, one small and one large medikit, no keys and no carried dragon bits. Only Venice masks advance the sampled ordinals.

**Established statically — native tick-0 reset.** Fresh campaign entry copies carried stock, not The Great Wall's live `save` counters. In Venice all seven fields of `save` start at zero, including `time` and `distance`; the first distance comparison is seeded at the authored Venice spawn, even for a placed fixture. Clock 76 and leaves 73 and 74 each start with timer 0, latch 0 and no active-list membership. The mine chain starts clear and all six mines are unspent and off the active list. The next-level counter reset is separate from the level's authored clock, leaves and mine placements.

**Established — membership.** A room check starts with the item's current membership and follows the local sector's horizontal and then vertical links. The horizontal lookup uses a boundary sector when the position is out of range; it does not search for a room whose header contains the point. Vertical transfer needs the appropriate link: the sample must meet or pass the sector floor to go down, or be strictly above the sector ceiling to go up. A room without the needed link can therefore remain the item's room. The room check and the stored floor are distinct measurements. On dry ground Lara refreshes her room from a point 381 above her origin; her stored floor can come from the lower room. The tiger adjusts to the current floor, and its final room check can use a point 512 above its origin. A placed helicopter retains its authored room until it moves; while active it rechecks at its new origin each tick.

**Observed examples.** In `pool-swim`, `pool-wade` and `tiger-cave`, Lara is 2–380 units below room 36's authored bottom in 271 samples. In each she stands on the stored floor in a sector linked down to room 37. Tiger 18 likewise retains room 36 below its authored bottom at ticks 512–532 of `pool-wade`. Helicopter 101 initially has its authored origin outside the vertical bounds of room 69, then moves to linked room 71 on the next tick. Across three scripts it retains room 72 for 537 samples after flying past that room's extent: the boundary-sector lookup need not supply another room just because the origin is outside. These examples compare the recorded memberships and positions with the authored rooms and links, not with bounding boxes inferred from the traces.

### Live statistics (Q-INT-01)

**Established — distance.** The previous position starts at Lara's authored spawn, before any placed-start override. A placed start does not change the zero starting total or that previous sample. At the end of Lara's update, after movement, object contact, weapon handling and her sector actions, add the three-dimensional distance from the previous sample to her resulting origin. Use game units: take the floor of the unsigned integer square root of the sum of the three squared coordinate differences. The square sum and the cumulative total both wrap at 32 bits; there is no distance cap. Keep the resulting origin as the next tick's previous sample. This measures net displacement, including a snap or a fall, not the lengths of the intervening motion steps.

**Established — fixture checks.** The Great Wall's previous sample is (62976, 1536, 23040) at tick 1. `stand` and `placed-stand` both add zero there, `pickup` adds 13301, `switch-door` adds 11592 and `placed-travel` adds 1581. Using that seed and the successive post-update positions reproduces distance at all 1980 sampled updates across those five records and `pool-swim`.

**Established — time and event counters.** The level clock adds one after Lara and the camera on each completed campaign logic tick, including neutral input; it uses a 32-bit unsigned counter without saturation. The Manor is the exception: it adds one only while the training timer is running, which is established statically. No other saved tally has an automatic per-tick increment: secrets, kills, ammunition used and hits, and medikit use change on their own gameplay events. In all six distance checks the clock equals the tick ordinal.

**Established — world hashing.** For each of the four digests start a separate FNV-1a-32 stream at 2166136261, with the same multiplier as the record hash. Feed only the specified bytes, with no separators or padding, and store the result as an unsigned decimal integer. Apply the live room, floor and box changes before hashing; the untouched file sections alone will not reproduce `world[0]` or `world[1]`.

## Scope and limits

The record excludes process addresses, handles, padding, heap/list pointers, wall-clock readings, frames between logic steps, renderer and sound buffers, and title/menu navigation. Schema 20 omits brains; schemas 21 and 22 include the fields above, not the complete navigation ledger. Schemas 20 and 21 do not sample dormant world items; schema 22 samples the placed boats and the specified clock, leaf and mine fields even when dormant, not all dormant items. Schema 22 counts occupied effects but no schema includes individual transient effects, all level-data words, current input sampler state, display preferences or complete saves. World hashes show differences but do not identify the changed sector by themselves. There is no separate generic pickup count or full ring setting. A trace verifies the sampled state, not an unrecorded route or an intermediate value omitted from the record.
