# M64 (MiSTer-derived FPGA core) TLB and the tlbcode boot failure

Author: CoreRead, 2026-11-19. Branch `m7-coreread`.

Scope: why the tr64 cart and a sibling project built on the libdragon fork's
TLB code units (`N64_TLBCODE`, fork commit `0822b98aa`) fail at the first call
into a unit on the user's ModRetro M64 (SummerCart64) but run in ares, and
what to do about it.

Rules observed: the core's source was read for facts about the platform's
behaviour only. No code from it is copied here or anywhere in this repository.
Every core fact cites file, line and commit. Facts that the source cannot
establish are labelled `[INFERENCE]` or `[UNMEASURED]`.

## 1. Result in one paragraph

With Status.KX set, the MiSTer core translates an **instruction fetch** through
the TLB only when bits 63:60 of the fetch address are below 8
(`rtl/cpu.vhd:1066-1067`, MiSTer-devel/N64_MiSTer `5725381`, introduced by
`0b3b778` on 2025-12-15). A kseg2 program counter as the compiler produces it,
`0xFFFFFFFFC1000000`, has bits 63:60 = `F`, so the core fetches it as an
**unmapped physical address** (`FetchAddr(31:0)`, masked to 29 bits). The
resident text at `0xC0001000` still runs because the unmapped path aliases:
`0xC0001000 & 0x1FFFFFFF = 0x1000`, which is also what the wired entry maps.
Units at `0xC1000000` alias to physical `0x01000000`, which is beyond RAM. The
CPU then executes a no-op-like sled up to `0xC3F00000`, where physical
`0x03F00000` is the RDRAM register space, and the word at `+0xC` reads as
`0xC0C0C0C0`, which decodes as `ll $0, -0x3F40($a2)`. That reproduces the
recorded state (EPC `C3F0000C`, BadVAddr `FFFFC0C0`, ExcCode 2) exactly
(section 5). The data side translates kseg2 correctly under KX, so only
instruction fetch is affected.

Two fixes follow from the source (section 7): clear KX (F1), or keep KX and
link units into kuseg below `0x80000000` (F2). Both are unmeasured on the M64.
The platform can be fingerprinted harmlessly by a mapped-versus-alias fetch
probe (section 7.3).

### 3.2 TLB array and lookups

| Aspect | Core behaviour | Reference |
|---|---|---|
| Entries | 32, each with PageMask (12 bits), VPN2 (27 bits, address 39:13), ASID (8), region (2 bits, address 63:62), G, V0/V1, D0/D1, C0/C1, PFN0/PFN1 (**20 bits each**: physical address bits 31:12), and a "random" flag. EntryHi fill bits 61:40 are not stored. | cpu_cop0.vhd:1114-1147, 305-318 |
| Page sizes | All seven: PageMask is stored with each bit pair collapsed (bit 2k+1 of the pair replicated), so only the legal masks work (4K 0x0, 16K 0x6000, 64K 0x1E000, 256K 0x7E000, 1M 0x1FE000, 4M 0x7FE000, 16M 0x1FFE000). | Global | One G bit per entry = EntryLo0.G AND EntryLo1.G. | cpu_cop0.vhd:1114 |
| Match | `(global OR EntryHi.ASID == entry ASID)` AND `(vaddr[39:13] & ~mask) == entry VPN2` AND `vaddr[63:62] == entry region`. The ASID compared is the **live EntryHi.ASID** (so TLBR, which loads EntryHi.ASID, changes later matches for non-global entries). The upper bits 61:40 of the fetch address are not compared. A sign-extended 32-bit EntryHi (`mtc0` of a kseg2 value) gives region = 3 and a sign-extended VPN2; a kseg2 address matches only an entry whose region is also 3. Entries written with positive values have region 0. | cpu_cop0.vhd:985-1011, 710-720 (EntryHi write); cpu.vhd:2253 (`mtc0` value sign-extended) |

| Instruction mini TLB | **One** entry, 4 KiB granular (virtual 39:12 + region 63:62). A lookup is requested only on a mini miss; the pipeline stalls for it. Cleared by `TLBInvalidate`. | cpu_TLB_instr.vhd:53-58, 68-70, 109-111, 145-157 |

| What clears the minis | Any executed TLBWI or TLBWR (any index), and any EntryHi write that changes the ASID. TLBR, TLBP, EPC, jumps, ERET and Index/Wired/PageMask writes do not. A TLBWI is applied to the array whether or not a lookup scan is in progress. | cpu_cop0.vhd:719, 911 |
| Random-miss emulation | Present but disabled: `RANDOMMISS` is tied to 0 in the core's top level. | N64.sv:823-824; cpu_TLB_instr.vhd:75 |

### 3.5 DMA then load

PI DMA writes RDRAM physical addresses; a load through a TLB mapping reads
the same RDRAM through the translated physical address, so it sees the data.
The only coherence rule is the usual one: the D-cache line for that physical
address must not hold older data. The fork's `read_blob`-style pattern
(`data_cache_hit_writeback_invalidate` on the kseg0 alias before the DMA,
`tlbcode.c:192`) covers both cases because the D-cache is physically tagged
(`cpu_datacache.vhd` tags by the translated address) and the option "Data
Cache from TLB" off removes the cache from mapped loads entirely. Nothing in
the source makes a mapped load after a DMA behave differently from an
unmapped one. **[UNMEASURED]** on the M64 itself.

## 5. Reconstruction of the recorded state

Record (from the user): ExcCode 2 (TLBL), EPC `C3F0000C`, BadVAddr `FFFFC0C0`,
Status `241094E3`, RA = the return address of the `jalr` into the unit.

1. `jalr` to `0xFFFFFFFFC1000000`: unmapped fetch of physical `0x01000000`
   (cpu.vhd:1067, 1151, 749). This is above the RAM window
   (`mem_address < 0x03F00000` is RAM in memorymux.vhd:320 but the DDR3 mux
   treats an address beyond the installed RAM as "behind RAM": reads return the
   contents at a fixed address just past RAM, writes are dropped,
   `DDR3Mux.vhd:327-334`). The instruction words returned are whatever that
   constant area holds. **[INFERENCE]** that they are zero, i.e. `sll $0,$0,0`.
2. The PC counts up by 4 per fetch with no carry out of bit 28
   (cpu.vhd:2136). From `0xC1000000` to `0xC3F00000` is 0x2F00000 / 4 =
   12,386,304 uncached fetches. **[INFERENCE]**: a stall of several seconds
   before the crash appears. HwAnalyst and the user can confirm from the
   screen timing.
3. At `0xC3F00000` the physical address is `0x03F00000..0x03FFFFFF`, the
   RDRAM register space (memorymux.vhd:346). The register RAM is read for
   offsets `<= 0x24`, and offset `0xC` (RDRAM_MODE) returns `value XOR
   0xC0C0C0C0` (RDRAMRegs.vhd:83-91, `read_xor`). Words at `+0x0`, `+0x4`,
   `+0x8` are whatever IPL3 wrote and execute as instructions (no fault was
   recorded; **[UNMEASURED]** whether they store anything).
4. The word at `+0xC` is `0xC0C0C0C0` when the mode register holds 0:
   opcode `0x30` (LL), rs = 6 (`$a2`), rt = 0, imm = `0xC0C0` = -0x3F40.
   `ll $0, -0x3F40($a2)` computes `a2 - 0x3F40`. With `a2 = 0` that is
   `0xFFFFFFFFFFFFC0C0`, whose low 32 bits are `FFFFC0C0` = the recorded
   BadVAddr. The base register is 0, so the core classifies the region as
   xuseg (cpu.vhd:2268-2269: base `<= 0x000000FFFFFFFFFF`), looks up
   `0xFFFFFFFFFFFFC0C0` (region 3), finds nothing, and raises a load miss:
   ExcCode 2, EPC = the address of the `ll` = `0xC3F0000C`
   (cpu_cop0.vhd:666, 833-866). A real VR4300 would also fault for that
   address (mapped ckseg3, no entry), so the exception itself is
   "legitimate"; only how the CPU got there is not.
5. Status `241094E3` = CU1, FR, KX|SX|UX, IE, plus EXL set by the exception:
   consistent with the SR saved at exception entry (HwAnalyst: `inthandler.S`
   94-95).

All three numbers (EPC offset `0xC`, the word `0xC0C0C0C0`, BadVAddr) come
out of one chain; none of them has a second explanation in the source.

What is not decided by the source:

- That `$a2` is 0 at the call. Nothing in the dispatch path writes it
  (HwAnalyst: `code_call`, `c0010ec0-c0010f48`); it is whatever
  `code_load`'s last `log_printf` left. The fatal screen's R06 will settle it.
  If `$a2` is not 0 the BadVAddr would differ, so the recorded value implies
  it was 0 (low 32 bits).
- What the constant area after RAM contains on the M64 (PSRAM-based, not the
  MiSTer DDR3). The chain needs it to execute without faulting until
  `0xC3F00000`. Any content that decodes to non-faulting instructions works.
- Whether the M64's RTL has exactly the MiSTer rule. The M64 RTL is not
  published; the match of three numbers is the evidence.
- The M64's setting of "Data Cache from TLB" and "DTLB Mini Cache" (menu
  options in the MiSTer core). Neither is implicated.

## 6. Other deviations from a VR4300 that the fork might meet

None of these explains the record. They are listed so the probe and any
later failure are checked against them.

1. Instruction fetch with KX=1 and PC bits 63:60 >= 8 is unmapped (the cause).
2. Instruction mini TLB: one 4 KiB entry; every 4 KiB page change in
   translated code costs a lookup of up to 32 clocks (a few clocks when the
   next page is mapped by the same or an adjacent entry because the scan
   starts at the last hit). Performance only. Data mini TLB: four 4 KiB entries.
3. Hit_Invalidate_I ignores the tag (over-invalidates) and is not translated.
4. TLBR/TLBP behaviour: TLBR dropped while a scan is in flight; PFN 20 bits;
   mask collapsed; VPN2 masked at write.
5. EPC overwritten on nested exceptions, refill vector chosen by ERL rather
   than EXL. Harmless for the fork because all four vectors branch to
   `inthandler` (`entrypoint_tlbcode.S`), but nested-exception diagnostics can
   show a clobbered EPC.
6. TLB translation of data uses the base register's region only; an
   address that crosses a region by the immediate is misclassified.
7. Physical addresses are masked to 29 bits after translation (cpu_cop0.vhd:1187).
8. No page size above 16M, no 36-bit physical addresses; EntryLo PFN bits above
   bit 25 are lost.
9. Nothing found that makes a CACHE on a mapped address fault or hang: I-cache ops are
   untranslated, D hit ops translate like loads (and are dropped when "Data
   Cache from TLB" is off).
10. libdragon xkphys accesses (`io_read`, `io_write`, `pi_cpu_read`:
    `0x9000...|addr`, HwAnalyst `src/dma.c:132,536,558`) are fine under KX=1
    but are invalid under KX=0 on both hardware and the core.

## 7. Workarounds

### 7.1 Candidates for "a way of writing and using the mappings that works on both"

Rejected because the source shows they cannot change the outcome:

- A sync step or more nops after TLBWI: the entry is stored correctly and
  the instruction side never consults it under KX=1 for a region-3 PC.
- Invalidating the instruction cache through kseg0 instead of the mapped
  range: Hit_Invalidate_I is not translated on the core and is not the fault.
- Avoiding data loads through the mapping: the data side translates kseg2
  correctly under KX.
- Different page sizes or entry layouts: the fetch is not translated at all,
  so nothing in the entry matters.

Accepted candidates:

**F1: clear KX|SX|UX in the tlbcode boot Status write** (`entrypoint.S:27`,
under `N64_TLBCODE_BOOT`). The core then runs the 32-bit rule
(cpu.vhd:1068), which maps kseg2 and kseg3 in kernel mode: this is the logic
that was the only one before `0b3b778`. Costs and risks:

- Resident text (`0xC0001000`) becomes truly translated. The instruction
  mini TLB has one entry, so resident code that crosses 4 KiB boundaries pays
  a lookup per boundary (3.2). **[UNMEASURED]**.
- libdragon's xkphys users must move to KSEG1 (`0xA0000000|addr` for
  `addr < 0x20000000`): `src/dma.c:132,536,558` (per HwAnalyst); `tlbcode_init`
  reaches this through `rompak`. Under KX=0 an xkphys access is an address
  error on hardware, a TLB lookup miss on the core.
- Any pointer in a 64-bit register must be properly sign-extended.
  Compiler-produced 32-bit pointers are.
- TLB refill vector becomes `0x80000000` instead of `0x80000080`; the fork
  already branches all vectors to `inthandler`.
- The snapshot probe's TLBR can be skipped while a fetch lookup is in flight
  (4.9): repeat and compare.

**F2: keep KX=1, link units into kuseg (below `0x80000000`)**, e.g. from
`0x50000000` (not `0x40000000`: the boot loop's invalid entries use
`0x4003E000 - 8192*i`, and `tlbcode.c:226` reuses `0x40000000 + slot*8192`).
A PC of `0x0000000050000000` has bits 63:60 = 0, so the core maps it
(cpu.vhd:1067) and the EntryHi written by `mtc0` of a positive value has
region 0 (matching). Data loads from there are region-mapped too
(cpu.vhd:2268). On real hardware kuseg is mapped in kernel mode in both
addressing modes. Costs:

- Changes: `tools/tlbcode.py:12-14` (`UNIT_BASE`, `UNIT_END`, stride), the
  linker script's unit sections and the `ASSERT`, tr64's
  `plat/n64/fatal.c:103` and `tools/fatal/decode.py:41`, `architecture.md`
  section 6, `docs/architecture.md:160-161`. The vector stubs
  (`lui k0,%hi(inthandler)`) already give positive addresses.
- `jal` cannot leave a 256 MiB region. Units call resident code directly
  (`architecture.md` section 6); resident text stays at `0xC0001000` and unit
  objects must be built with `-mlong-calls` (or the resident text must move
  into the same 256 MiB region as the units, which brings back translated
  resident fetch with the 1-entry mini TLB; not recommended).
- Resident text keeps running by alias as today (speed as in 4.4).
- No change to libdragon I/O (KX stays 1).
- On a real VR4300 the layout is unchanged in behaviour.

F2 has the smaller blast radius in the fork (HwAnalyst agrees) but touches the
tool, link and diagnostics; F1 is one line plus the xkphys change.
Both depend on the instruction side honouring the TLB, which the source says it
does in those two cases and the probe in 7.3 will test on the console.

### 7.2 Probes for these (HwLane)

P1, P2, P3 as in 7.3 and the Hit_Invalidate_I colour test; HwLane's ROM
already includes them. P2 (KX=0) validates F1, P3 (kuseg, KX=1) validates F2.

### 7.3 Fingerprint

A mapped-versus-alias instruction fetch. Properties of the test: no exception
is taken on any platform, it modifies one TLB entry (restored), and it uses two
free RAM pages.

1. Before anything else touches RAM: invalidate the I-cache by index
   (`inst_cache_invalidate_all`-style kseg0 index ops).
2. Pick two free 8 KiB-aligned RAM pages A and B (physical) not covered by
   the wired entries (kseg3 is used so the probe VA never collides with
   `0xC0000000 + 2*W MiB`).
3. Write via KSEG1 (uncached): at A `jr $ra; addiu $v0,$zero,2`
   (`0x03E00008, 0x24020002`), at B `jr $ra; addiu $v0,$zero,1`
   (`0x03E00008, 0x24020001`).
4. Map with TLBWI at an unused index (31): `EntryHi = 0xE0000000 + A`
   (`mtc0` sign-extends: region 3), PageMask 0, `EntryLo0 = (B>>6)|0x1B`,
   `EntryLo1 = 1`. The virtual address `0xE0000000+A` has physical alias A
   under the core's unmapped path (`(0xE0000000+A) & 0x1FFFFFFF = A`).
5. With KX=1 (the fork's setting) `jalr` to the sign-extended pointer
   `0xFFFFFFFFE0000000+A`. Result `v0`:
   - **1**: translated through the entry: real VR4300, ares, or a core
     without the `0b3b778` rule.
   - **2**: the core's unmapped alias: affected M64/MiSTer core.
   - Any exception or hang: stop; platform unknown; use the safe fallback.
6. Restore the entry to an invalid state (`EntryHi = 0x40000000 + 8192*31`,
   EntryLo 0) and restore EntryHi/PageMask. Run the same probe with a kuseg
   VA (P3) and with KX=0 (P2) to choose between F1 and F2 at run time instead
   of building for one core.

Ares and real hardware both give 1; the fingerprint does not and need not
tell them apart (both translate the fetch). To pick a mapping style, only the
three probe results matter. Further, source-derived differences that can be
checked harmlessly but are **[UNMEASURED]**: TLBR returning EntryLo PFN
bits 29:26 as 0 (core, `cpu_cop0.vhd:932`) versus the full 24-bit PFN on
hardware; Hit_Invalidate_I clearing an index regardless of tag (core) versus
only on a tag match (hardware). PRId (`0x0B22`), Config/Status reset values and
RDRAM_MODE's `^0xC0C0C0C0` read are the same on the core and hardware and are
not discriminators.

### 7.4 Fallback without run-time paging

The user's proposal: require the Expansion Pak on the M64, map every unit
once at boot with entries of a page size the core handles, backed by Expansion
Pak frames.

Unit slots are at `0xC1000000 + n*0x80000` (`tools/tlbcode.py:12-14`; 32
slots, max 62 pages per unit). An entry maps a pair of equal pages; the pair
must be aligned to twice the page size, and a PFN must be aligned to the page
size. With p 4 KiB pages per unit (1..22 for about 21 units):

| Page size | VA span of one entry (pair) | Entries per unit | Physical granule per page | Fits 512 KiB slot stride? |
|---|---|---|---|---|
| 4 KiB | 8 KiB | ceil(p/2) | 4 KiB | yes |
| 16 KiB | 32 KiB | ceil(p/8) | 16 KiB | yes |
| **64 KiB** | 128 KiB | **1** (p <= 32) | 64 KiB (EntryLo0 first 16 pages, EntryLo1 next 16) | yes |
| 256 KiB | 512 KiB | 1 | 256 KiB | yes, but physical waste |
| 1 MiB and up | 2 MiB and up | spans 4 slots | 1 MiB contiguous | no: slots 512 KiB apart would need 512 KiB physical spacing |

- Entry budget: 32 minus W wired (1 or 2 for the resident text) = 30 or 31
  usable (the fingerprint probe uses one more only during boot). 4 KiB pages
  need the sum over units of ceil(p/2) entries; 21 units cost at least 21 even
  at one page each, so the 4 KiB layout fits only if that sum is at most 30
  (for example about 60 pages in total, 240 KiB, spread so that few units have
  more than 2 pages). The stated range of 1..22 pages does not guarantee it.
  64 KiB pages need exactly one entry per unit: 21 entries plus W = 22-23
  of 32.
- Memory with 64 KiB pages: each unit needs ceil(p/16) frames of 64 KiB
  (aligned). Lower bound 21 x 64 KiB = 1.3125 MiB (all units <= 16 pages), upper
  bound 21 x 128 KiB = 2.625 MiB (all units 17-22 pages). The tail of each
  64 KiB frame beyond the unit's size is unmapped from the unit's slot (the slot
  just has no content there) and can be given to the heap through kseg0 if the
  allocator splits it; otherwise count the whole frame. The actual code bytes
  are 4 KiB x (sum of p): about 0.34 MiB at p=4 on average, up to 1.8 MiB.
- Memory with 16 KiB pages (entries ceil(p/8), 1..3 per unit): frames of
  16 KiB, so the waste is at most 12 KiB per unit (252 KiB for 21 units) and
  the footprint is close to the code size. Choose per unit the smallest page
  size that keeps the sum of entries within the budget: units of 1..8 pages
  use 16 KiB pages (one entry), units of 9..22 pages use 64 KiB pages (one
  entry); total entries 21 + W, memory bounded by the 64 KiB case above.
- Source: Expansion Pak frames are at `0x80400000-0x807FFFFF` (physical
  `0x400000`+), which is addressable by the 20-bit PFN and the 29-bit mask
  (cpu_cop0.vhd:1187). The 8 MiB RAM mode depends on the M64's RAM-size setting
  (MiSTer: `RAMSIZE8_2x`, `DDR3Mux.vhd:328`); the M64's behaviour is
  **[UNMEASURED]**.
- No remap at run time: after boot the TLB is never rewritten, so the
  stale-mini and TLBR-in-flight hazards (3.2, 6.4) cannot arise from remapping.
  That is the only thing this fallback buys: it removes run-time TLBWIs (the
  unit load/unload path) from the risk set. Loading all units at boot costs one
  DMA of the unit blob (sum of p x 4 KiB, 0.3-1.8 MiB) before the first frame.
- **It does not avoid the instruction-fetch rule.** Fetching from the mapped
  slots needs F1 or F2 just the same. If neither F1 nor F2 can make the core
  fetch through the TLB, the only fallback that does not depend on the core is
  a build in which the units are linked into resident text at kseg0 (unmapped
  and cached), needing RAM for the sum of the unit sizes (0.3-1.8 MiB) in
  addition to the resident text. That build variant does not exist in the
  fork's linker script (`n64_tlbcode.ld` places units at `0xC1000000+`) and
  would be a new link layout; it is stated here as the final fallback only.
